# Android 12L audio attribution and call-access audit

Audited `android12/{base,av,Telecomm}`, all at `android-12.1.0_r27`: Android 12L/API 32. The folder name does not make this a full initial Android 12/API 31 audit; initial-release coverage is limited to the patch history and phone-account permission follow-up below. Framework audio construction, relevant native audio policy, and Telecom service admission were inspected. PermissionController qualification, vendor HAL implementations, and physical two-way audio were not verified for this tag. See the [Android 11 audit](ANDROID11_SOURCE_AUDIT.md) for the earlier baseline and the [implementation plan](ANDROID_COMPATIBILITY_PLAN.md#3-implement-the-older-cellular-audio-backend) for the release matrix.

## Construction and attribution differences

[`AudioRecord.Builder.setContext()`](https://android.googlesource.com/platform/frameworks/base/+/android-12.1.0_r27/media/java/android/media/AudioRecord.java#635) exists. The [record constructor](https://android.googlesource.com/platform/frameworks/base/+/android-12.1.0_r27/media/java/android/media/AudioRecord.java#453) obtains `context.getAttributionSource()` when supplied, otherwise `AttributionSource.myAttributionSource()`. Recording therefore accepts an explicit helper context carrying the actual helper UID and its corresponding operation package.

`AudioTrack.Builder` has no `setContext()`. The [track constructor](https://android.googlesource.com/platform/frameworks/base/+/android-12.1.0_r27/media/java/android/media/AudioTrack.java#817) passes [`PlayerBase.getCurrentOpPackageName()`](https://android.googlesource.com/platform/frameworks/base/+/android-12.1.0_r27/media/java/android/media/PlayerBase.java#535) to native setup. This reads [`ActivityThread.currentOpPackageName()`](https://android.googlesource.com/platform/frameworks/base/+/android-12.1.0_r27/core/java/android/app/ActivityThread.java#2356), which delegates to the initial Application. Wrapping only the AudioManager context does not change this track attribution.

[`AttributionSource.myAttributionSource()`](https://android.googlesource.com/platform/frameworks/base/+/android-12.1.0_r27/core/java/android/content/AttributionSource.java#195) combines `Process.myUid()` with `ActivityThread.currentOpPackageName()`. This differs from Android 11, where the class and both builder setters are absent. It agrees with the documented setter introductions: record at API 31, track at API 34. Keep per-builder runtime detection for vendor differences.

The current implementation already handles this split. `AudioBuilderContext` supplies an explicit context where supported and prepares default attribution when the setter is absent. `ModernAudioContext.prepareProcessAttribution()` wraps the existing Application base context, overrides its operation package and attribution source, and verifies the resulting defaults while preserving the Application, its ordinary package metadata, and the Linux UID. A setter-invocation or adapter failure remains an audio-setup failure. This source audit establishes which constructor inputs the adapter changes; it does not establish runtime hidden-field access or successful modem delivery.

## Direct cellular audio remains the relevant backend

The audited source has no `getCallUplinkInjectionAudioTrack()`, `getCallDownlinkExtractionAudioRecord()`, `CALL_AUDIO_INTERCEPTION`, or modern call-redirection mode. Their absence is expected on this tag. The [shell manifest](https://android.googlesource.com/platform/frameworks/base/+/android-12.1.0_r27/packages/Shell/AndroidManifest.xml) requests `RECORD_AUDIO`, `CAPTURE_AUDIO_OUTPUT`, `MODIFY_PHONE_STATE`, and `MODIFY_AUDIO_SETTINGS`; actual device grants still require inspection.

For downlink, [native input admission](https://android.googlesource.com/platform/frameworks/av/+/android-12.1.0_r27/services/audiopolicy/service/AudioPolicyInterfaceImpl.cpp#593) checks recording access and requires output-capture access for `VOICE_DOWNLINK`. [`ServiceUtilities`](https://android.googlesource.com/platform/frameworks/av/+/android-12.1.0_r27/media/utils/ServiceUtilities.cpp#70) attributes that source to `OP_RECORD_INCOMING_PHONE_AUDIO`; [the framework's default](https://android.googlesource.com/platform/frameworks/base/+/android-12.1.0_r27/core/java/android/app/AppOpsManager.java#2703) is allowed. Recording permission checks still apply.

For uplink, [native policy](https://android.googlesource.com/platform/frameworks/av/+/android-12.1.0_r27/services/audiopolicy/managerdefault/AudioPolicyManager.cpp#1102) selects `INCALL_MUSIC` when the explicitly selected output is telephony TX, the format is linear PCM, the usage is voice communication (or the stream is music), and call audio is accessible. [Telephony TX admission](https://android.googlesource.com/platform/frameworks/av/+/android-12.1.0_r27/services/audiopolicy/service/AudioPolicyInterfaceImpl.cpp#360) checks `MODIFY_PHONE_STATE`. The gateway can use ordinary builders and `setPreferredDevice(telephonyTx)` with those privileges; enumeration and preference alone do not establish permission or hardware support.

### Related permission-grant history

The supplied Android 12 patch [commit `f0f97d56da256039619dea6325592a48a5535e9b`](https://android.googlesource.com/platform/packages/modules/Permission/+/f0f97d56da256039619dea6325592a48a5535e9b), “Defined roles for sandboxed components providing on-device system intelligence features,” adds PermissionController roles with `minSdkVersion="31"`. `SYSTEM_AUDIO_INTELLIGENCE` and `SYSTEM_AMBIENT_AUDIO_INTELLIGENCE` include `CAPTURE_AUDIO_OUTPUT`, `CAPTURE_MEDIA_OUTPUT`, `CAPTURE_VOICE_COMMUNICATION_OUTPUT`, and `RECORD_AUDIO` among their grants. Both roles are hidden, exclusive, system-only, and have configured default holders. This supplies audio-capture grants to system intelligence components and leaves this gateway's Shizuku/shell permission recipe unchanged. The note is based on the supplied patch; matching Android 12 PermissionController role qualification and grant execution were not audited here.

## Call access differs from Android 11

[`InCallController`](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-12.1.0_r27/src/com/android/server/telecom/InCallController.java#1820) admits a service as `IN_CALL_SERVICE_TYPE_NON_UI` when it declares neither UI nor car-mode UI and has either `CONTROL_INCALL_EXPERIENCE` or permitted `MANAGE_ONGOING_CALLS`. The latter is checked through [`PermissionChecker`](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-12.1.0_r27/src/com/android/server/telecom/InCallController.java#2314). This provides a non-UI admission path alongside the user's dialer on this tag. A test companion-list override is not required by that classification branch, so the override health flag alone does not determine whether the service can bind. Required service declarations and actual callbacks remain separate checks.

This differs from the audited Android 11 baseline's app admission, which led to the default-dialer requirement. Keep the Android 11 requirement scoped to that tag rather than extending it to API 32.

### Release history and test evidence

The supplied [commit `4cc5a541d2b93d6bbc0427681ca2fbb175333ebb`](https://android.googlesource.com/platform/packages/services/Telecomm/+/4cc5a541d2b93d6bbc0427681ca2fbb175333ebb), “Binds to 3rd-party InCallService with MANAGE_ONGOING_CALL permission,” adds this admission branch. Its original implementation uses `PermissionChecker.checkPermissionForPreflight()`.

The supplied follow-up [commit `e3f82cc7a1f79c6bce1e3aa35d96d83aeb329307`](https://android.googlesource.com/platform/packages/services/Telecomm/+/e3f82cc7a1f79c6bce1e3aa35d96d83aeb329307) changes both `InCallController.isAppOpsPermittedManageOngoingCalls()` and [`TelecomServiceImpl.hasManageOngoingCallsPermission()`](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-12.1.0_r27/src/com/android/server/telecom/TelecomServiceImpl.java#859) to `checkPermissionForDataDeliveryFromDataSource()`, with an attribution chain from Telecom's context to the app UID/package. It retains the same non-UI admission branch. Both supplied commits are included in the initial public Android 12/API 31 release, as identified with the patches: the attribution-aware check is already part of that release. The local full-tag audit remains `android-12.1.0_r27`/API 32, where both resulting methods were checked. This patch history does not constitute a full API 31 audio audit.

The patch adds `InCallControllerTests.testBindToService_ThirdPartyApp()`. It defines a third-party service requiring `BIND_INCALL_SERVICE`, with no UI metadata and no `CONTROL_INCALL_EXPERIENCE` grant, allows its `MANAGE_ONGOING_CALLS` AppOp, and verifies two bindings: the system dialer first, then the third-party non-UI service. The [retained test in the audited tag](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-12.1.0_r27/tests/src/com/android/server/telecom/tests/InCallControllerTests.java#918) mocks the newer PermissionChecker result and verifies the same bindings. This is Telecom unit-test evidence for concurrent admission, not an audio-routing test. The commit message also lists `ThirdPartyInCallServiceAppOpsPermissionTest` as a validation command; that CTS test is not included in the supplied patch and was not inspected or run here.

Implementation correction: `CallAccessRequirements` accepts the enabled non-UI service and allowed `MANAGE_ONGOING_CALLS` on API 31+ without requiring a companion override or a dialer role. The subsequent [Android 13 and current Android 17 checks](ANDROID13_SOURCE_AUDIT.md#current-framework-follow-up-android-17) confirm this admission path on those releases. Calling permissions remain required. The override health flag remains diagnostic, and setup still attempts the existing override operation; its absence no longer blocks readiness. API 30 keeps its default-dialer requirement. Regression coverage includes API 31–37 with no override or role, plus loss of AppOp, service availability, or calling permissions.

Validation (2026-10-12): `:privileged:testDebugUnitTest` passed all 23 app-side tests, including the new readiness regression. The upstream Telecom/CTS tests and physical-device binding/audio were not run in this check.

## Phone-account lookup permission

Source follow-up (2026-10-25): initial Android 12 already protects [`TelecomManager.getPhoneAccount()`](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-12.0.0_r1/src/com/android/server/telecom/TelecomServiceImpl.java#320), including queries used only to inspect account capabilities. Compatibility change `183407956` [enables the check for apps targeting API 31+](https://android.googlesource.com/platform/frameworks/base/+/android-12.0.0_r1/telecomm/java/android/telecom/TelecomManager.java#1021). Targeted checks of [Android 13](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-13.0.0_r1/src/com/android/server/telecom/TelecomServiceImpl.java#357), [Android 16](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-16.0.0_r1/src/com/android/server/telecom/TelecomServiceImpl.java#645), and [Android 17](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-17.0.0_r1/src/com/android/server/telecom/TelecomServiceImpl.java#695) confirm the same gate. These checks do not constitute full audits of those releases.

[`canGetPhoneAccount()`](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-12.0.0_r1/src/com/android/server/telecom/TelecomServiceImpl.java#2437) accepts the default/system dialer or relevant SIM call manager, otherwise requiring `READ_PRIVILEGED_PHONE_STATE` or `READ_PHONE_NUMBERS`. The calling method separately exempts shell; Android 17 also bypasses this gate for callers holding its privileged Telecom UI permission. Non-UI InCallService admission, `MANAGE_ONGOING_CALLS`, and `READ_PHONE_STATE` do not exempt an ordinary companion app from the lookup permission check.

The gateway's `CellularEndpoint.isCellular()` performs this lookup under the app UID to check `PhoneAccount.CAPABILITY_SIM_SUBSCRIPTION`. Shizuku's helper permissions do not cover that call. Keep `READ_PHONE_NUMBERS` in setup's phone-permission grants while takeover is enabled.

## Muting and route failures

[`AudioService.adjustStreamVolume()`](https://android.googlesource.com/platform/frameworks/base/+/android-12.1.0_r27/services/core/java/com/android/server/audio/AudioService.java#2818) requires `MODIFY_PHONE_STATE` to mute the voice-call or Bluetooth SCO stream. [`USAGE_VOICE_COMMUNICATION`](https://android.googlesource.com/platform/frameworks/base/+/android-12.1.0_r27/media/java/android/media/AudioAttributes.java#1628) maps to the voice-call stream. Consequently, muting that stream must be checked for effects on injected audio as well as handset output; source permission admission does not establish independent handset suppression.

Applied routing reaches AudioFlinger patch creation and the [playback thread](https://android.googlesource.com/platform/frameworks/av/+/android-12.1.0_r27/services/audioflinger/Threads.cpp#4512), then device `createAudioPatch()` or legacy stream routing parameters. The [HIDL adapter](https://android.googlesource.com/platform/frameworks/av/+/android-12.1.0_r27/media/libaudiohal/impl/DeviceHalHidl.cpp#302) invokes the HAL's create/update operation. [`installPatch()`](https://android.googlesource.com/platform/frameworks/av/+/android-12.1.0_r27/services/audiopolicy/managerdefault/AudioPolicyManager.cpp#7167) receives its status, but [`setOutputDevices()`](https://android.googlesource.com/platform/frameworks/av/+/android-12.1.0_r27/services/audiopolicy/managerdefault/AudioPolicyManager.cpp#6457) ignores that return value and returns a mute wait duration. Some route failures therefore need native logs and actual remote audio to detect. Successful construction, a device preference, or increasing frame counters do not prove delivery.
